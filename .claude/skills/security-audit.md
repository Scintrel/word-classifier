# 安全审计技能

对项目代码进行安全审计，检查以下四个方面的安全隐患，按风险等级输出报告。

## 检查标准

### 标准 1：敏感信息泄露

**要检查的位置**：
- 代码中硬编码的密码、API 密钥、Token、私钥（如 `password = "123456"`、`apiKey = "sk-xxx"`）
- 数据库连接字符串中明文密码
- 日志输出中的敏感信息（`console.log(password)`）
- 测试文件、注释、错误信息中残留的真实密码/密钥

**判断规则**：
- 任何看起来像真实凭证的字符串（密钥长度 > 10、随机字符）→ 🔴 高危
- 占位符（如 `your-api-key-here`、`xxxxx`、`TODO`）→ 🟢 安全
- 本项目的 AI 配置（DeepSeek API Key）应存储在本地数据库 settings 表中，不应写死在代码里

### 标准 2：代码注入风险

**SQL 注入**：
- 用字符串拼接构造 SQL 的地方（如 `"SELECT * FROM t WHERE x = '" + input + "'"` 或反引号 `${input}`）→ 🔴 高危
- 正确做法：参数化查询 `db.prepare("... WHERE x = ?")` + `bind([input])`
- 注意：`LIMIT ${size}`、`ORDER BY ${col}` 这类拼接——即使参数是数字也要标记 🟡（防御性编程）

**命令注入**：
- 拼接字符串调用 `exec()` / `spawn()` / `child_process`（如 `exec("ls " + userInput)`）→ 🔴 高危
- 路径拼接未校验（如 `readFileSync(userPath)` 未检查目录穿越 `../`）→ 🟡 中危

**XSS（界面脚本注入）**：
- React 中直接使用 `dangerouslySetInnerHTML` → 🔴 高危
- 把用户输入不经处理直接渲染为 HTML → 🔴 高危
- Electron 中 `webview` 标签、未关闭 `nodeIntegration`、未启用 `contextIsolation` → 🔴 高危

### 标准 3：配置文件明文敏感信息

**要检查的文件**：
- `package.json`、`electron-builder.yml`、`vite.config.ts` 等配置文件
- `.env`、`.env.local` 等环境变量文件（如果存在）
- 任何 `.json` / `.yml` / `.toml` / `.ini` 配置文件

**检查内容**：
- 配置中写死的 API 密钥、密码、Token → 🔴 高危
- 私有的服务器地址、内网 IP → 🟡 中危
- 打包配置中是否包含了不该打包的敏感文件（如 `.env`、测试数据）→ 🟡 中危

**判断规则**：
- 本项目的 AI API Key 应通过设置界面输入、存本地数据库，绝不出现在配置文件中
- 如果配置文件里只有结构没有真实密钥 → 🟢 安全

### 标准 4：其他安全隐患

- **IPC 安全**：Electron IPC handler 是否对来自渲染进程的输入做了校验？`ipcMain.handle` 中直接使用 `event.sender` 发来的路径读文件 → 🟡 中危
- **文件路径安全**：用户提供的文件路径是否校验了目录穿越（`../../`）？→ 🟡 中危
- **密码明文存储**：密码/密钥明文写入数据库或文件 → 🟡 中危
- **弱加密或不加密**：应该加密的数据没有加密 → 🟡 中危
- **权限过大**：Electron 窗口配置中 `webPreferences` 开启了不必要的高权限 → 🟡 中危
- **依赖漏洞**：package.json 中依赖版本过旧（可提示检查 `npm audit`）→ 🟢 提示
- **错误信息泄露**：错误信息中暴露了内部路径、数据库结构 → 🟢 提示
- **临时文件残留**：密码、密钥写入临时文件后未删除 → 🟡 中危

## 风险等级定义

| 等级 | 含义 | 处理方式 |
|------|------|---------|
| 🔴 高危 | 真实凭证泄露 / 可利用的注入漏洞 | 必须立即修复 |
| 🟡 中危 | 潜在风险，需要特定条件才能被利用 | 建议修复 |
| 🟢 提示 | 安全隐患不大，但值得改进 | 可选择性修复 |

## 工作流程

1. **确定审计范围**——用户可能指定某个文件、某个目录，或全部项目代码
2. **按四个标准逐文件检查**
3. **交叉验证**——对疑似泄露的字符串，验证它是否真的是密钥（长度、随机性、上下文）
4. **生成风险报告**（格式见下）

## 报告格式

```
## 安全审计报告

### 📊 总体结论
- 审计范围：X 个文件
- 🔴 高危：X 个 | 🟡 中危：X 个 | 🟢 提示：X 个
- 一句话总结：项目整体安全状况

### 🔴 高危风险
| 文件 | 位置 | 问题 | 修复建议 |
|------|------|------|---------|

### 🟡 中危风险
| 文件 | 位置 | 问题 | 修复建议 |
|------|------|------|---------|

### 🟢 安全提示
（列表形式）

### ✅ 做得好的地方
（值得保持的安全实践）
```

## 修复模式

用户说"修复"时，按风险等级从高到低处理。修复原则：
- 绝不引入新的安全风险
- 修复密钥泄露：把密钥从代码移到设置/环境变量，并提醒用户更换已泄露的密钥
- 修复注入：改用参数化查询 / 输入校验
- 修复后重新审计一遍，确认风险已消除
